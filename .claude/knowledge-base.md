## Hard Rules
- [042026] In Electron overlay.html init(), register IPC listeners (onSetDeText, onOverlayShown) BEFORE any await — events arrive the moment the overlay is shown; blocking on await fetchProfiles() causes them to be missed. [Source: empirical 042026]
- [042026] suppressAutoDetect after any clipboard copy (IPC copy-to-clipboard) must be 500ms, not higher. 2000ms blocks the next real fan message if copied quickly. The primary guard against re-trigger is `lastClipboard === text` (IPC always updates it); 500ms is only backup. [Source: empirical 042026, confirmed 042126]

## Platform & Tool Rules
- [042026] Node.js fetch() in Electron 28 main process hangs indefinitely even when the server responds in <1s — always use https.get + req.setTimeout() for IPC handlers in main.js. [Source: empirical 042026]
- [042026] DeepL Pro key (no :fx suffix) must use https://api.deepl.com/v2/translate — api2.deepl.com times out and api-free.deepl.com returns "wrong endpoint" error. [Source: empirical 042026]
- [070126] Auf Windows/PowerShell schlaegt `git commit -m "$(cat <<'EOF'...EOF)"` mit Exit-Code 1 fehl (redirect-Operator `<` unbekannt in PS). Korrekte Syntax fuer mehrzeilige Commit-Messages: `git commit -m @'...Zeilen...'@` (PowerShell Single-Quoted-Heredoc; schliessend `'@` muss zwingend an Spalte 0 stehen). Gilt fuer alle multi-line native-exe-Argumente in PowerShell 5.1 und hoher. [Source: empirical 070126 -- Exit code 1 bei Bash-heredoc-Syntax im PowerShell-Tool]

## Project Patterns
- [042126] copyText() in overlay.html must use window.chatpro.copyToClipboard() (IPC), not navigator.clipboard.writeText(). Only IPC updates lastClipboard and sets suppressAutoDetect in main.js -- browser clipboard API bypasses the watcher entirely. [Source: empirical 042126, v1.9.3 bugfix]
- [042126] looksGerman() must not include words common in English chat: so, am, was, hat, hey, gut, an, war, da, im, er, sie, es, ja, nein, okay, alter. These caused false positives on English fan messages. Only keep unambiguously German words. [Source: empirical 042126, v1.9.2 bugfix]
- [042126] scheduleTranslate() (DeepL 800ms timer) must be cancelled with clearTimeout(translateTimer) at the start of generateReplies(). Otherwise the input translation box updates while the user is reading generated replies. [Source: empirical 042126, v1.9.2 bugfix]

## Known Failure Modes
- [042226] macOS Screen-Recording-Permission-Dialog in Electron-Apps wird durch `active-win` getriggert, auch ohne explizites getSources/desktopCapturer. Wer keine Screen-Capture-Features braucht, darf `active-win` nicht importieren -- Dependency komplett entfernen, nicht nur Code auskommentieren. [Source: empirical 042226, v1.9.6 bugfix -- Mac-Chatter bekamen Screen-Recording-Prompt obwohl Screenshots disabled waren]
- [060326] Werte, die in fetch()-HTTP-Header gehen (besonders `x-api-key`), muessen vor Verwendung auf printable-ASCII bereinigt werden (`.replace(/[^\x21-\x7E]/g, '')`). HTTP-Header sind Latin-1-only; ein kopierter API-Key mit unsichtbarem Unicode-Zeichen (Zero-Width-Space, Smart-Quote) laesst fetch sofort werfen: "Failed to read the 'headers' property from 'RequestInit': String contains non ISO-8859-1 code point." `.trim()` allein reicht NICHT. Bereinigung sowohl am Eingabepunkt (saveSettings) als auch am Verwendungspunkt (callClaude). [Source: empirical 060326, v1.9.7 bugfix -- Irish gespeicherter Key mit non-Latin1-Zeichen crashte Generate]
- [060726] Jeder String, der in den Claude-API-Request-Body geht (Fan-Nachricht, systemPrompt-Bloecke, Profilfelder), muss vor `JSON.stringify` von unpaarigen UTF-16-Surrogaten bereinigt werden. Ein per Copy-Paste abgeschnittenes Emoji hinterlaesst ein halbes Surrogat; `JSON.stringify` serialisiert es als unpaares `\uXXXX`, die API antwortet mit HTTP 400 "no low surrogate in string". Daten-abhaengig + deterministisch (kein Server-/Overload-Problem). Fix: `stripLoneSurrogates()` in `callClaude` -- sowohl auf `userMsg` als auch auf alle `text`-Felder in `system`-Block-Arrays anwenden. Schwesterregel zur Latin-1-Header-Bereinigung (060326). [Source: empirical 060726, v2.0.1-pending -- ChatPro Generate HTTP 400; installierte v2.0.0 + alle Builds byte-sauber; Bug rein aus Laufzeit-Input; Regex per Node-Test verifiziert]
- [060326] UI-Renderer, die Konfigwerte (apiKey) einmalig in `init()` cachen, muessen den Wert bei leerem Cache via IPC live nachladen (z.B. `getApiKey()`). Electron-Fenster, die nur hide/show werden, lassen `init()` nicht erneut laufen -- gecachte Variable bleibt leer, `if (!cached) openSettings()`-Guard wird zur Endlosschleife. [Source: empirical 060326, v1.9.7 bugfix]

## Prompt Caching & Model Selection
- [060326] Bei wiederholten Claude-API-Calls mit großem, festem System-Prompt IMMER Prompt-Caching nutzen: `system` als Array von Blöcken, statischen Teil mit `cache_control: { type: 'ephemeral' }` markieren, dynamischen Teil (Profil/Mood/Goal) in separaten ungecachten Block dahinter. Spart 90% auf dem gecachten Input bei Treffern (5-Min-TTL). KEIN Beta-Header nötig: Standard-5-Min-Caching ist seit 2024 GA, `cache_control` wirkt direkt im Body. Nur der optionale 1-Stunden-Cache braucht `anthropic-beta: extended-cache-ttl-2025-04-11`. [Source: empirical 060326, v2.0.0; docs-verifiziert 060426 gegen platform.claude.com]
- [060326] Opus 4.8 kostet 2026 ~1,67x von Sonnet 4.6 ($5/$25 vs $3/$15 pro MTok). Fuer qualitaetsgetriebene, revenue-relevante Generierungsaufgaben ist der Aufpreis vernachlaessigbar. Mood/Klassifikations-Calls auf Haiku 4.5 ($1/$5) auslagern. [Source: empirical 060326, v2.0.0 Kostenanalyse]
- [070126] Modell-Verfuegbarkeit NIE aus dem claude-api-Skill-Cache ableiten -- dieser ist sessions-gebunden und kann Monate hinterherhinken (claude-sonnet-5 und claude-fable-5 waren beide GA waehrend der Cache sie nicht listete). Bei jeder Modellentscheidung live pruefen: platform.claude.com/docs oder GET /v1/models. Aktueller Stand (070126): claude-sonnet-5 GA mit Adaptive Thinking + 1M Kontext; Intro-Preis $2/$10 per MTok bis 31.08.2026, danach $3/$15. [Source: empirical 070126 -- Skill-Cache sagte "nicht existent", WebFetch auf platform.claude.com widerlegte das]
- [071626] Generalisiert [070126] auf ALLE Vendor-API-Limitierungen (nicht nur Claude-Modelle): Wenn eine dokumentierte Einschraenkung (z.B. "Fansly hat kein Webhook") eine Kosten-/Architekturentscheidung (Polling statt Webhook) begruendet, live im eigenen Vendor-Dashboard/Account pruefen statt einer Monate alten Doku-Notiz zu vertrauen -- weder das eigene INTEGRATIONS.md noch die oeffentlichen Vendor-Docs kannten die neuen Fansly-Webhooks bei onlyfansapi.com, nur das Account-Dashboard zeigte sie. Zusatzbefund: geteilte Namespaces (Fansly + OnlyFans unter demselben Vendor-Key) teilen sich auch den Credit-Pool -- hoher Verbrauch in einem Bereich kann von einem anderen Bereich desselben Kontos stammen. [Source: empirical 071626, chatpro-ops -- Fansly-Poll-Cron (10-Min, ~31 Calls/Account/Lauf) durch /webhooks/fansly ersetzt, commit a40ab9d]
- [062126] Prompt-Cache-Minimum: `cache_control` wirkt erst ab einem Mindest-Prefix -- Opus 4.8/4.7/4.6/4.5 UND Haiku 4.5 = 4096 Token; Fable 5/Sonnet 4.6 = 2048; Sonnet 4.5 = 1024. Kuerzere Prefixe cachen still gar nicht (cache_creation=0, kein Fehler). Folge fuer chatpro-ops: kurze System-Prompts (QA ~1100, Openers ~700 Token) cachen auf Opus/Haiku NICHT -> Caching ist dort kein Hebel, Batch-API (flat 50%, kein Token-Minimum, asynchron) schon. [Source: reference 062126, claude-api Skill verifiziert]

## Prompt Rules
- [042126] LLM-Prompt-Regeln fuer optionale Stil-Features (Vokaldehnung, Slang, Emojis) MUESSEN einen expliziten Frequenz-Cap enthalten (z.B. "~1 in 4 replies max, most replies have zero"). Permissive Formulierungen wie "when excited" werden als Standardmodus gelesen, nicht als Ausnahme -- Modell wendet das Feature auf fast jede Antwort an. [Source: empirical 042126 -- v1.9.5 Vokaldehnung in 3/3 Varianten trotz "when excited/cute"-Regel; User-Korrektur erzwang expliziten Cap]
- [042126] Im deutschen Chat-Register sind "digga", "alter", "bruder", "ey mann", "mach ma" stark maennlich codiert und DUERFEN in weiblicher Stimme nicht vorkommen. Weiblich-codiert: "hihi", "ach", "ohje", "oh mann", "suess", Vokaldehnung, 🥺🙈🫶-Emojis. Gilt fuer jeden Translator-Prompt der einen Gender-Character simuliert. [Source: empirical 042126 -- v1.9.5 User-Feedback "etwas zu maennlich fuer mein Geschmack"; Yapper-Prompt enthielt digga/alter als empfohlenen Slang]

## Railway & Server Operations
- [072926] ChatPro-Max `/api/deepl` (Railway monitoring-relay-production) hatte `source_lang` fest auf 'DE' verdrahtet und ignorierte das `lang`-Feld, das der Overlay-Client seit v2.0.7 schon mitschickt -- die Server-Haelfte des Multi-Sprachen-Rollouts fehlte. Symptom war sprachabhaengig und irrefuehrend: ES-Text wurde trotzdem meist korrekt uebersetzt (DeepL kam trotz falschem source_lang klar), IT-Text kam bei kurzen/mehrdeutigen Saetzen unveraendert zurueck (DeepL "Original == Uebersetzung"-Fallback wenn source_lang=DE auf echtem Italienisch erzwungen wird). Diagnose-Trick: den Vendor (DeepL) direkt mit denselben (falschen) Parametern aufrufen wie der Backend-Code, um den Bug deterministisch zu reproduzieren, bevor man einen Client-Bug vermutet. Fix: `lang` -> DE/ES/IT server-seitig explizit mappen (commit 4560904, ChatPro-Max/main), nach Deploy live verifiziert fuer alle drei Sprachen. Reiner Server-Fix -- kein neuer Overlay-Build noetig. [Source: empirical 072926, v2.0.7 Rollout-Luecke]
- [060226/060526] Mitarbeiter-Accounts IMMER ueber POST /api/users/create anlegen (Body: username, employeeName; Passwort wird auto-generiert + nur einmal zurueckgegeben). NIEMALS direkten Supabase-INSERT verwenden. Der Endpoint aktualisiert In-Memory-Map UND Supabase atomar -- Login sofort gueltig ohne Server-Redeploy. Direkter INSERT erzeugt einen Row in der DB, der Cache kennt ihn aber nicht → /api/login meldet "Invalid credentials". Username-Konvention: Vorname klein (irish, rhona, alvin, paul). [Source: empirical 060226 + 060526 -- Irish-INSERT-Incident bestaetigt Problem; rhona/alvin/paul via Endpoint alle sofort HTTP 200 ohne Redeploy]
- [060226] Username-UNIQUE-Constraint in Supabase users-Tabelle ist case-sensitive (Irish != irish). UPSERT mit ON CONFLICT (username) erkennt unterschiedliche Casings NICHT als Konflikt und legt eine zweite Row an. Bei Mitarbeiter-Anlage Casing vorab festlegen (immer Vorname klein) und nie ueber direkten SQL-UPSERT anlegen. [Source: empirical 060226 -- irish-UPSERT legte Row neben Irish an statt ihn zu ersetzen]
- [060426] Ein neuer Railway-Service aus dem ChatPro-Max-Server-Code antwortet mit HTTP 502 ("Application failed to respond"), wenn SUPABASE_URL/SUPABASE_KEY fehlen -- server.js macht bei fehlenden Vars process.exit(1), der Prozess crasht beim Boot. 502 nach Deploy = zuerst Env-Vars + Deploy-Logs pruefen (erwartet "Supabase client initialized"), nicht den Code. [Source: empirical 060426 -- ChatPro J Backend lieferte 502 bis alle 5 Env-Vars gesetzt waren, danach /health 200]

## Git & Build Operations
- [072926] Ein Repo mit Windows-ungueltigem Pfad (z.B. Ordnername mit trailing space, auf NTFS illegal) lehnt den Working-Tree-Checkout komplett ab ("invalid path"), auch in Git-Bash -- der Working-Tree-Write selbst schlaegt fehl, nicht nur Explorer. Umgehung: kein Checkout noetig, stattdessen per Git-Plumbing direkt am Object-Store arbeiten: `git show HEAD:pfad > tmp`, Datei editieren, `git hash-object -w tmp`, `git ls-tree HEAD` nehmen und den Blob-SHA fuer den geaenderten Pfad per `sed` ersetzen, Ergebnis durch `git mktree` jagen, `git commit-tree <tree> -p HEAD -m msg`, dann `git push origin <sha>:branch`. [Source: empirical 072926, ChatPro-Max-Repo hat einen "public /"-Ordner mit trailing space]
- [061026] GitHub Actions `electron-builder --mac` DMG-Schritt ist sporadisch flaky auf macos-latest-Runnern: `hdiutil: detach failed - No such file or directory` ODER `dmgbuild FileNotFoundError: /Volumes/<Name>/.background/background.tiff`. Beides sind DMG-Volume-Races, kein Code-/Konfig-Problem. Fix: denselben Run via `POST /actions/runs/{id}/rerun-failed-jobs` neu starten -- geht beim ersten Re-run fast immer durch. 3x bestaetigt. [Source: empirical 061026, 3x confirmed -- master v2.0.1 hdiutil, agency v2.0.1-agency background.tiff, v2.0.5 release-race]
- [062126] GitHub-Release-Race: Windows-Assets per curl ans Tag-Release laden WAEHREND die Mac-CI (softprops/action-gh-release) dasselbe Tag-Release anlegen will, erzeugt zwei Release-Objekte fuer denselben Tag. softprops scheitert beim Finalisieren mit `Validation Failed: already_exists field tag_name` (Mac-Build selbst gelingt, dmg/zip landen im Draft). Fix: den fehlgeschlagenen Job via `POST /actions/runs/{id}/rerun-failed-jobs` neu starten -- softprops findet dann das bestehende tag-gebundene Release und updatet es; danach verwaisten Draft loeschen. Schwester zur DMG-Flakiness-rerun-Regel [061026]. Vermeidung kuenftig: entweder CI das Release anlegen lassen ODER das Release VOR dem Tag-Push anlegen. [Source: empirical 062126, v2.0.5-Release]
- [062126] Overlay-Secrets build-time injizieren statt hartcodieren: Distribuierte Electron-Apps koennen Secrets nicht wirklich verstecken (asar trivial entpackbar), aber man haelt sie aus dem git-Repo/GitHub raus: `scripts/gen-secrets.js` schreibt beim Build gitignored `src/secrets.js` aus `process.env`; package.json `prebuild`/`prestart`-Hooks; Mac-CI via GitHub-Repo-Secrets. Build OHNE gesetzte Env-Vars -> gen-secrets warnt "EMPTY" und die App geht mit leeren Keys raus (Feature still inert, aber wirkungslos). Namens-Falle: ops-Backend/Railway nennt den Log-Key `LOG_KEY`, das Overlay `OPS_LOG_KEY` -- gleicher Wert. Quellcode-verifiziert 072726 gegen chatpro-ops/src/config.js + server.js: `config.rulesKey = process.env.RULES_KEY` (server.js:346, schuetzt `/api/training/rules/active` via `x-rules-key`-Header), `config.logKey = process.env.LOG_KEY` (server.js:804, schuetzt `/api/chatter-log` via `x-log-key`-Header). Beide Werte im Klartext im Railway-Dashboard unter chatpro-ops -> Variables einsehbar. [Source: empirical 062126, v2.0.5; verifiziert 072726 gegen server.js]
- [060426] Git-Worktrees teilen den Tag-Namespace des Eltern-Repos. git tag vX schlaegt fehl wenn der Tag schon existiert, und git push remote vX pusht dann den ALTEN Commit auf den der Tag zeigt, nicht den aktuellen HEAD. Folge: CI baut falschen Code. Fix: im Worktree immer einen eigenen Tag-Namen verwenden der explizit auf den gewuenschten Commit zeigt (git tag v2.0.0-agency sha). Bestehende master-Tags nie verschieben (gemeinsames .git). [Source: empirical 060426 -- ChatPro J Mac-Build: v2.0.0 zeigte auf master-Commit dd2a4b6 statt Agentur-Commit; korrigiert via v2.0.0-agency auf 06c3426]
